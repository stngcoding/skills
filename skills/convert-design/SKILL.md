# convert-design

Converting a Figma frame to code is two jobs that matter equally:

1. **Visual fidelity** — every color, spacing, border, gradient, shadow, and radius matches the design *exactly*, not approximately.
2. **Codebase integration** — the output uses the project's real framework, design tokens, shared widgets, and conventions, so it looks like a teammate wrote it.

**You will almost always be invoked with nothing but a Figma dev link — no "watch the border" or "match the gradient."** That is the normal case, not a degenerate one. Do not wait to be told which properties matter: *every* property matters. The promise of this skill is a complete, exact reproduction from a bare link. If your output only nails the properties the prompt happened to name, you have failed — the prompt naming nothing is the same job as the prompt naming everything. Sweep every node for every paint, stroke, effect, and opacity (Step 1e) and reproduce each exactly.

The single biggest cause of "it doesn't match" is trusting the wrong source. Read the next section before anything else.

## The fidelity principle: the code preview is a hint, not the truth

> **Note:** The Figma MCP always returns a React + Tailwind code preview regardless of your target stack. The Tailwind class names below describe how to read MCP output — they are not prescribing output syntax. Translate every extracted *value* into whatever idiom your project uses.

`get_design_context` returns a React + Tailwind code preview. **It is a structural reference for layout and hierarchy — it is NOT an accurate source for visual properties.** The preview is generated by snapping Figma values onto Tailwind's scale, which silently destroys exactly the properties users notice:

- **Borders** — a *bracketed* border carries the exact values, so read them straight off it. `border-[1.5px] border-[rgba(255,255,255,0.4)] border-solid` means width **1.5px** (not 1) and a solid white stroke at alpha **0.40** (not solid white, not rounded to 0.5). Transcribe the width and the *entire* color **including its alpha** — the most common stroke bug is *under*-reading these: snapping `1.5`→`1`, or dropping the alpha by mapping the color onto a bare named token (`#FFFFFF` / `white` silently throws away the `0.4`). A *bare* `border` with no bracket is the red flag — there the width and alignment really were lost, so recover them from the screenshot/variables. Two things a bracket never encodes: stroke **alignment** (inside/center/outside) and whether the paint is secretly a **gradient** stroke flattened to its *average* color. Suspect a gradient **only when the screenshot shows one edge distinctly brighter than the rest** — on a uniformly-lit border the flat `rgba(...)` *is* the real color, so transcribe it; don't estimate a rim that isn't there. (When it genuinely is a gradient, read direction/intensity from the screenshot and tell the user the stops are estimated — see `visual-fidelity.md`.)
- **Gradients** may snap to `bg-gradient-to-r` (8 fixed directions) — losing the real angle — appear as an exact `bg-[linear-gradient(...)]`, or, when the gradient is on a stroke or is subtle, be **flattened to a single flat color**. You cannot tell paint *type* from the code: treat any fill or stroke that shows a visible sheen/falloff in the screenshot as a gradient, even if the class says `border-solid` or `bg-[#hex]`.
- **Colors** carry a `var(--token,#hex)` fallback that is usually exact, but a flattened/blended color may be rounded.
- **Shadows** may snap to `shadow-md` (a Tailwind preset that has nothing to do with the design) or appear exact as `shadow-[...]`.

So the rule: a *preset* class (`border`, `shadow-md`, `bg-gradient-to-r`, `rounded-lg`) is a red flag — recover the real value from `get_variable_defs` or the high-res screenshot. An *arbitrary-value bracket* (`border-[1.5px]`, `shadow-[0px_8px_24px_rgba(...)]`) is exact — transcribe it verbatim, never round.

**`references/visual-fidelity.md` is the heart of this skill** — the full red-flag table plus exact extraction-and-reproduction rules for every visual property (expressed as CSS values you translate into your stack). Read it before implementing any node with a border, gradient, shadow, blur, or non-trivial opacity.

## URL parsing

Extract `fileKey` and `nodeId` from the URL:
- `https://figma.com/design/:fileKey/:fileName?node-id=:nodeId` → convert `-` to `:` in nodeId (e.g. `1-23` → `1:23`)
- Branch URLs (`/branch/:branchKey/`) → use `branchKey` as the fileKey

## Workflow

### Step 1 — Extract from Figma

**1a. Map the node tree:**
```
get_metadata(fileKey, nodeId)
```
Identify major sections and their child node IDs from the XML. You'll fetch design context per-section, not all at once.

Flag any nodes typed `COMPONENT_SET`, `COMPONENT`, or `INSTANCE` — these require two extra steps: (a) call `get_design_context` on the instance node itself (not just its parent) to reveal assets nested inside it, because assets inside components are invisible from the parent frame's response; and (b) enumerate their variants in Step 1f.

**1b. Fetch design context per-section** (never the whole root frame — it truncates):
```
get_design_context(fileKey, nodeId: "<section-nodeId>")
```
Use the React+Tailwind output for **structure only**: hierarchy, flex direction, gaps, padding, ordering. For repeating items (list rows), fetch one in detail and replicate. Remember the fidelity principle — do not transcribe its border/gradient/shadow classes as gospel.

**1c. Fetch the exact tokens:**
```
get_variable_defs(fileKey, nodeId)
```
These are the design team's real values (`icon/default/secondary: #949494`, `radius/md: 12`). They are the authoritative source for any property bound to a variable — prefer them over anything in the code preview.

**1d. Take a high-res screenshot** at `maxDimension: 2048` — the full frame plus any section with a gradient, glow, border, or shadow. This is your ground-truth visual reference and your tie-breaker whenever the code preview is ambiguous.

**1e. Build a fidelity inventory — always, regardless of the prompt.** This step is mandatory and is the contract: walk *every* node and record *every* visual property on it, not just the ones that look interesting or that the request mentioned. A property you don't write down is a property you'll drop. This is what separates a matching conversion from an approximate one:
```
Node "Card" (5:12): fill #0C1838, border 1px INSIDE rgba(46,242,255,0.24), radius 20, shadow 0 16 48 rgba(0,0,0,0.5)
Node "CTA" (5:30): fill linear-gradient(135deg, #2EF2FF 0%, #C8EA80 100%), radius 9999
Node "Glow" (5:40): backdrop-blur 40px
```
For each entry, follow `references/visual-fidelity.md` to get the precise value. If a property is ambiguous in the preview, resolve it now from variables or the screenshot — not later.

**1f. Enumerate component variants (if any COMPONENT_SET nodes were found):**
Call `get_metadata(fileKey, componentSetNodeId)` on each COMPONENT_SET. Each child in the XML is one variant. Record:
- The variant property names and values (e.g. `State=Default`, `State=Hover`, `Type=Primary`, `Size=Small`)
- The visual differences between variants — color changes, opacity, icon swaps, text changes, visibility toggles

Do NOT implement only the default variant and stop. Every variant maps to an interactive state (hover, focus, active, disabled, selected, loading, etc.) that must be wired up in Step 3. A component missing its non-default states is an incomplete implementation, even if the default looks pixel-perfect.

### Step 2 — Discover the project's stack and conventions

This skill is framework-agnostic. Before writing code, learn the target:

- **Framework & styling system**: Detect from the project — look for config files (`package.json`, `pubspec.yaml`, `*.config.*`), styling patterns (CSS modules, Tailwind, SASS, styled-components), and component conventions. If the user named a target framework, honor it. The visual-fidelity rules are framework-agnostic; you map the extracted value into whatever idiom the project uses.
- **Design tokens**: Find the project's color/spacing/typography/radius/gradient/shadow definitions. Common spots: `lib/**/theme/`, `lib/**/constants/`, `styles/`, `tailwind.config.*`, `*tokens*`, files named for "Colors", "Spacing", "Typography", "Radius", "Gradient", "Shadow". Map each Figma variable from Step 1c onto its project-token equivalent.
- **Shared widgets/components**: List the component/widget directories and read constructors so you reuse what exists (buttons, cards, switches, dropdowns) instead of rebuilding.
- **Similar screens**: Find an existing screen with comparable structure and match its state management, imports, and composition.
- **Asset handling**: Find the *one* way this project carries icons/images and commit to it — an inline SVG-path dictionary/component, a generated accessor over an `assets/` dir, a static `public/` folder + image component, raw paths, etc. Every asset you bring in will live in that single place (Step 3), so pin the idiom down now: mixing idioms is exactly what leaves orphaned, divergent asset files behind.

  **Assets inside component instances are invisible from the parent frame's response.** If Step 1a flagged INSTANCE nodes, call `get_design_context(fileKey, instanceNodeId)` for each one now. The inline `<svg>` blocks, image fills, and vector nodes that live inside a component will not appear in the parent section's output — they are silently absent unless you fetch the instance explicitly. Build the full asset list from both the section responses *and* these per-instance responses before classifying anything.

  **Asset classification (decide this in Step 2, before touching any file):** Projects typically have 2–3 distinct asset slots, and you must route each Figma asset into exactly one of them. For every asset in the design, run this classification in order:

  1. **Is the Figma node type VECTOR, BOOLEAN_OPERATION, or a GROUP of only vectors?**
     The MCP returns these as an inline `<svg>` block with `<path d="…">` data.
     - **≤32 px, single fill/stroke color (monochrome glyph)** → it is a UI icon. Extract the `d="…"` value from the `<path>` tag and place it in the project's icon system (discovered in Step 2 — e.g. a name → path-string dictionary, an icon component, or a sprite sheet). Do NOT save the raw Figma export as a standalone file.
     - **Multi-color, decorative, or >32 px** → inline the adapted `<svg>` directly in the component or relevant constants file.

  2. **Is the Figma node a raster fill — a RECTANGLE/FRAME with an image-fill, or the MCP returned a `.png`/`.jpg` asset URL?**
     → It is a raster image. Download it to the project's static asset directory and reference it via the project's image element or component (e.g. `<img>`, or the framework's optimized image primitive). Use explicit `width`/`height`, or a sized parent with `fill`.

  3. **Already covered by an existing component?** (avatar, logo, product photo — check if a component already handles it)
     → Reuse the component; don't duplicate the asset.

  The distinguishing signal is where in the design each asset lives:
  - Icon buttons, nav glyphs, status indicators → almost always category 1 (icon system).
  - Profile photos, product images, hero illustrations, logo raster layers → almost always category 2 (raster via image element).
  - When unsure, look at the Figma node type in `get_metadata` output: `VECTOR` → category 1; `RECTANGLE`/`FRAME` with image fill → category 2.

**Build a reuse + token map:**
```
Reusable: <Button>, <Card>, <Toggle>, <Dropdown>
Tokens: color → <Colors>.xx · spacing → <Spacing>.xx · type → <Typography>.xx · radius → <Radius>.xx · gradient → <Gradients>.xx
```

### Step 3 — Build the blueprint and implement

Document the layout with exact values, then implement node by node:
```
Root: 393×852, padding 20, gap 16, vertical
├── Header: fill×hug, horizontal, space-between
│   ├── Title: 20/700, color text-primary
│   └── Icon: 24×24
└── Card: fill×hug, padding 16, radius 20, border 1px inside accent@24%, shadow lg
```
- Read `references/layout-mapping.md` for Figma auto-layout → widget/element translation.
- For every border, gradient, shadow, blur, or opacity, apply `references/visual-fidelity.md` — do not freehand them.
- Use discovered tokens for every value. Reuse shared components from your map.
- **Never redraw vectors with CSS or hand-coded geometry.** When `get_design_context` returns an inline `<svg>` block for a vector node (VECTOR, BOOLEAN_OPERATION, or a group of vectors), that block contains the real path data (`d="…"`). Extract the path string verbatim and place it in the project's asset idiom (icon dictionary, inline SVG, etc.). Do not approximate the shape with `border-radius` tricks, box-shadows, CSS pseudo-elements, or made-up `<path>` coordinates — CSS geometry cannot reproduce arbitrary Figma vectors, the result will visibly differ, and the discrepancy grows worse with organic shapes, compound paths, and icons with variable stroke weights. If `get_design_context` on the parent section did not return the inline SVG (common when the vector is inside a component instance), call `get_design_context(fileKey, instanceNodeId)` explicitly to retrieve it — see Step 1a and the asset discovery note in Step 2.
- **Implement all component states (from Step 1f).** For each variant discovered, wire up the corresponding interactive state — `:hover`, `:focus`, `:active`, `disabled`, a selected/pressed prop, a state enum value in the data model, etc. Match to the project's convention from Step 2 (CSS pseudo-classes, state props, event handlers, etc.). Never leave non-default states unimplemented.
- **Bring each asset into the project exactly once, in the project's idiom — never hotlink the Figma URL, leave it as a const, or keep a second divergent copy.** The asset URLs in the `get_design_context` response are **temporary — they expire in ~7 days** — so they can't be referenced live; and the inline `<svg>` the MCP hands back is *codegen output*, not a shippable file: its paints are `var(--token, #hex)` placeholders the parent was meant to set, it carries `preserveAspectRatio="none"`, and it's sized in percentages. That is an intermediate. Pick the asset's single home from the convention you found in Step 2 (the project's static asset directory + image element; or an inline icon system), adapt the vector into that idiom **once** — e.g. resolve a `var(--stroke-0, #FDFDFD)` paint to the real color, or to `currentColor` when the same glyph is tinted differently per context (a send icon that's white on a dark button and dark on a light one) — and reference it only from there. **That adapted version is now the single source of truth — do not also commit the raw export beside it.** Two copies of one vector drift apart immediately: the live component gets corrected while the stray file keeps the broken `var(...)`/stretched form, and the next person can't tell which is real. The signature of this bug is an asset file that **nothing imports** while the component re-inlines its own copy — dead, divergent, and often a violation of the project's own convention (a project that inlines its icons should never gain a stray `public/icons/*.svg` at all). Swapping in a built-in lookalike (Material/Lucide/Heroicon, emoji, hand-drawn `<path>`) is a separate fidelity loss — the shape, weight, and detail won't match. Only approximate if an asset genuinely can't be fetched, and flag it.

### Step 4 — Verify against the design (loop until clean)

Run this checklist; fix and re-run until every item passes:

**Correctness**
- [ ] Static analysis / lint / typecheck passes (run the project's configured checker)
- [ ] Components/elements follow the project's convention (not throwaway helper functions if the project forbids them)
- [ ] All component variants from Step 1f are implemented — every interactive state (hover, active, disabled, selected, loading, etc.) is wired up in code, not just the default

**Token hygiene**
- [ ] No raw color literals, spacing numbers, font sizes/weights, or radius values where a project token exists — and every Figma value with no matching token is flagged to the user
- [ ] All shared components from the reuse map are actually used, not rebuilt

**Assets (single source of truth)**
- [ ] Assets inside INSTANCE nodes were fetched by calling `get_design_context` on each instance explicitly — not assumed to be covered by the parent frame's response
- [ ] No vector was redrawn with CSS or hand-coded geometry — every vector's `d="…"` path was extracted from the inline `<svg>` the MCP returned and placed in the project's asset idiom
- [ ] Every asset you brought in is referenced by shipped code — grep its name and confirm something imports it; an asset nothing uses is an orphan, delete it or wire it
- [ ] Exactly one representation per vector, in the project's idiom — no raw Figma export (with `var(...)` paints / `preserveAspectRatio="none"`) left sitting next to the adapted or re-inlined copy of the same icon
- [ ] **Classification is correct**: every ≤32 px monochrome glyph lives in the project's icon system (not as a PNG in the static directory); every raster/photo uses the project's image element (not inlined as `<svg>`). A 24×24 icon button rendered as a raster image is a classification bug — the path string should be in the icon system instead.

**Visual fidelity** (the part naive conversions fail — verify each against the Step-1 fidelity inventory)
- [ ] **Borders**: width is the exact Figma stroke (not snapped to 1px — keep fractions like 1.5); **color and its alpha transcribed exactly** (e.g. `rgba(255,255,255,0.4)` stays 40% translucent — alpha not dropped by mapping onto a solid token, not rounded); stroke alignment (inside/center/outside) accounted for in sizing; per-side and per-corner values preserved
- [ ] **Gradients**: type (linear/radial/angular) correct; direction derived from the real angle/handles (not snapped to a cardinal direction); every color stop and position reproduced
- [ ] **Shadows**: offset x/y, blur, spread, and color+opacity all match; inner vs drop shadow correct; multiple shadows all present
- [ ] **Blur**: layer blur vs background/backdrop blur distinguished and mapped correctly
- [ ] **Opacity**: layer opacity vs fill alpha distinguished — applied at the right level so it doesn't bleed onto children or borders incorrectly
- [ ] **Nothing skipped because the prompt didn't name it**: every property in the Step-1e inventory is reproduced, including the ones the request never mentioned (subtle fills, faint borders, inner shadows, low-opacity glows)
- [ ] **Screenshot comparison**: render the built UI (or, if no runtime is available, carefully eyeball your planned decoration) and compare side-by-side with the Step-1 screenshot; reconcile every visible difference until you cannot tell them apart

## Gotchas

These are quick reminders. For the full treatment of any visual property, go to `references/visual-fidelity.md`.

- **get_design_context truncates on large frames.** Always call per-section using child node IDs — never on the root. If a section still looks truncated, split it further.
- **Figma line-height is absolute px; most frameworks need a multiplier.** Divide Figma line-height by font size (`24px` on `16px` → `1.5`). The exact font specs come from the `These styles are contained in the design:` line in the design-context response — more reliable than the Tailwind `leading-`/`text-` classes.
- **Per-corner radius doesn't map to a single uniform `rounded` value.** When corners differ, set each corner individually.
- **Component instances can override the master.** Read the instance node's own values, not the master component's.
- **Icons/vectors come back as temporary asset URLs and inline codegen SVG.** Small shapes (indicators, dots, logos) export as image/SVG links that expire in ~7 days, and the inline `<svg>` is codegen form (placeholder `var(...)` paints, `preserveAspectRatio="none"`) — materialize each asset once in the project's idiom and reference it from there (see Step 3). One vector = one representation: if you adapt the codegen SVG for the project, don't also leave the raw export as a second file — they drift, and an asset nothing imports is dead weight. Don't ship the raw Figma URL, redraw vectors as borders/decorations, or swap in a built-in icon.
